# 领域层规范

适用：具有业务规则、不变量、生命周期和一致性要求的模型。简单 CRUD 不要求为满足目录形式引入复杂 DDD 模式。

## 模型与边界

- **DOMAIN-01｜必须**：使用统一业务术语，模型和方法表达业务意图；状态机、单位、计费和风险语义在相关 Spec 明确，代码与契约一致。
- **DOMAIN-02｜必须**：聚合边界围绕需要共同保持成立的业务约束设计；仅持有维护该约束需要的最小状态，不把所有历史、步骤、大文本和技术上下文放入聚合。
- **DOMAIN-03｜必须**：状态变化通过业务行为执行，由行为保证不变量；禁止依赖入口“记得检查”，禁止任意 setter 绕过规则，不暴露可写内部集合。
- **DOMAIN-04｜必须**：明确合法迁移、终态、重复调用、取消及失败语义。运行生命周期与规划／执行等阶段分开，不用一个枚举混淆两种维度。
- **DOMAIN-05｜推荐**：事务通常围绕聚合设计；确有同库原子更新多个聚合的需求时记录理由，不为坚持形式拆坏一致性。

## 值对象与数据语义

- **DOMAIN-06｜必须**：值对象在构造或受控工厂校验空值、范围、单位、精度及币种；不允许产生无效对象再期待调用方修复。
- **DOMAIN-07｜必须**：值对象不可变；record 的集合和可变成员需防御性复制。equals/hashCode 体现一致业务语义，不以对象引用或未规范化精度替代值相等。
- **DOMAIN-08｜必须（预算）**：区分额度、已用、预留和未知用量；拒绝超额度的新动作，同时允许如实记录已产生的实际超额及待核对用量。
- **DOMAIN-09｜必须（风险规则）**：规则评估同时考虑身份、资源、参数、数据敏感性及副作用；不只相信模型输出或远端工具标记，“只读”也可能是敏感导出。

## 服务、端口与框架隔离

- **DOMAIN-10｜必须**：领域层不依赖 Spring、Spring AI、ORM、HTTP、观测或线程调度框架；不使用 Spring Data 聚合基类、Spring Assert、@Transactional 或持久化注解建立领域行为。
- **DOMAIN-11｜必须**：领域服务表达不自然属于单个实体的业务规则；纯计算保持确定性。确有外部领域契约时依赖抽象端口，并明确 I/O 语义，不同时宣称它是纯函数。
- **DOMAIN-12｜必须**：领域只拥有属于领域语义的端口，通常包括领域仓储。模型生成、检索、工具执行、流和审计等用例协作契约默认归应用层，不以端口数量体现领域完整性。
- **DOMAIN-13｜禁止**：领域对象发起 SQL、HTTP、模型或工具调用，或通过全局容器获取技术实现；时间相关规则通过明确时间参数或可控时间来源验证。

## 领域事件

- **DOMAIN-14｜必须（事件）**：事件描述已经发生的业务事实并保持不可变，不携带可变实体引用；没有消费或可靠交付需求时允许直接返回行为结果，不为每个字段修改创建事件。
- **DOMAIN-15｜必须（跨上下文事件）**：通过公开集成事件表达契约，明确事件 ID、类型、版本、主体及必要租户上下文；不直接暴露内部模型。持久交付与去重由应用和基础设施协作实现。
- **DOMAIN-16｜必须**：区分领域事件、审计、状态日志和事件溯源。只有明确采用以事件重建状态的设计，才称为事件溯源；回放不得重新执行写工具。

## 验证

- **DOMAIN-17｜必须**：关键规则无需启动 Spring 即可测试；覆盖合法／非法迁移、边界数据、重复调用、金额与预算、集合封装和异常行为。
- **DOMAIN-18｜必须**：通过依赖检查及评审验证框架隔离；不能以“record 已生成”证明深不可变，也不能把行覆盖率当成不变量已验证。
