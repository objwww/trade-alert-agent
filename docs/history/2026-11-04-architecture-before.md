# 架构规范

适用：系统设计、Java 后端开发、重构与评审。本文同时约定应用层和 Agent 编排边界。

## 架构与依赖

- **ARCH-01｜必须**：先阅读目标模块、调用方、相关实现及契约，确认业务和数据流后修改；修复问题覆盖共享路径，避免只修单个入口。
- **ARCH-02｜优先**：复用现有能力、标准库和平台机制；按已知需求增加复杂度，不预建通用框架、空模块或无用途的适配层。
- **ARCH-03｜推荐**：以模块化单体和业务上下文组织代码。是否拆 Maven 模块、微服务或多 Agent，以边界、所有权和实际收益决定。
- **ARCH-04｜必须**：源码依赖向业务内核收敛；domain 不依赖其他工程层或技术框架；application 不依赖 interfaces 或 infrastructure 的具体实现。
- **ARCH-05｜必须**：interfaces 通过应用用例进入系统，不直接操作聚合、Mapper、数据库、模型或工具执行客户端。bootstrap 只负责装配与启动。

```text
interfaces → application → domain
infrastructure → application.port / domain 契约
bootstrap → 各层，仅装配
```

上述箭头表示源码依赖。运行时应用可以通过端口调用基础设施实现。

## 职责与端口

- **ARCH-06｜必须**：接口层负责协议、结构校验和身份提取；应用层负责用例、授权协调和执行编排；领域层负责业务规则与不变量；基础设施层负责技术实现。
- **ARCH-07｜必须**：端口按使用方和业务语义归属。领域仓储及真正的领域契约放 domain；模型、流、工具、检索和审计等用例协作端口默认放 application.port。
- **ARCH-08｜禁止**：向领域模型泄露 Spring AI、ORM、HTTP、Micrometer 等 SDK 类型，或为满足“所有端口都在 domain”将 Prompt、追踪和调度细节塞入领域。
- **ARCH-09｜必须**：Spring AI 等执行 SDK 限制在明确的适配包；A2A 等入口 SDK 只用于协议适配。装配类的例外不能演变为业务代码的绕行入口。
- **ARCH-10｜必须**：上下文之间通过显式 API 或集成事件协作，不访问对方内部聚合、Mapper 和存储实现。检查循环依赖和越界访问，两者分别验证。
- **ARCH-11｜推荐**：只共享真实复用、语义稳定的最小类型；不将全部错误码、分页和工具类集中成无边界 common 模块。

## 应用层与执行控制

- **ARCH-12｜必须**：应用层编排用例，领域层判断业务合法性。查询可通过应用查询端口直接取得读模型，不强制装载聚合，也不返回接口层类型造成反向依赖。
- **ARCH-13｜必须**：业务事务保持短小，模型、远程工具、外部 HTTP 和异步等待放在事务外；采用准备、外部执行、结果提交的分段流程，并验证事务实际生效。
- **ARCH-14｜必须（Agent）**：明确应用循环与 SDK 工具循环的执行控制权；每次模型及工具调用都受授权、预算、次数、超时、取消和审计控制，防止内部循环绕过外层检查。
- **ARCH-15｜必须（计费或配额调用）**：执行前预留，执行后结算；并发下原子控制总额度；未知用量保守记录，不得因失败重试无限释放预算。
- **ARCH-16｜必须（可恢复任务）**：持久化执行意图、状态及结果；处理调用前崩溃、外部成功但本地提交失败和重复调度。多实例还需明确执行权、接管和过期写回防护。
- **ARCH-17｜必须（外部副作用）**：区分成功、确定失败和结果未知。取消只承诺已实现的停止语义，不承诺撤销外部已完成动作；未知写结果不得盲目重试。
- **ARCH-18｜必须**：授权在可信执行边界落实；模型、检索材料、工具描述及第三方文档不能授予额外权限。恢复执行前重新验证已撤销的权限和已过期审批。

## 演进与验收

- **ARCH-19｜必须**：锁定相互兼容的 Java、Spring Boot、Spring AI 及依赖／插件版本，使用对应版本文档；不得混用不同版本 API。
- **ARCH-20｜必须**：架构检查覆盖实际模块，关键规则用合法和越界样例验证；工具不能证明的事务行为、语义或权限，通过测试和评审补足。
- **ARCH-21｜推荐**：重大边界和技术取舍记录 ADR；当前模块、信任边界及部署写入 ARCHITECTURE.md；具体状态机、阈值及契约放项目 Spec。

评审重点：职责归属、依赖方向、权限执行点、事务范围、外部副作用、预算、恢复及实际验证证据。
