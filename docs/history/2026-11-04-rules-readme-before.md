# Rules 使用说明

适用范围：Java / Spring 后端及采用 Spring AI 的 Agent 服务。整理依据：《AI Agent 工程规范 v2.1》修订稿。日期：2026-11-01。

本目录保留开发时反复适用的约束，供项目团队及编码助手使用。强制规则在所述场景成立时执行；推荐规则允许结合现状取舍。Agent、SSE、MCP、A2A、向量库和多实例条款只在项目具备对应能力时适用，不要求为了符合规范引入这些能力。

## 文件与适用范围

| 文件 | 内容 | 何时阅读 |
| --- | --- | --- |
| [01-architecture.md](01-architecture.md) | 架构、依赖、模块、应用层和 Agent 编排边界 | 开发、重构和评审前 |
| [02-coding-style.md](02-coding-style.md) | 命名、格式、Java 用法、异常、日志与并发 | 修改代码前 |
| [03-interface-layer.md](03-interface-layer.md) | HTTP/RPC、DTO、校验、授权、兼容性、异步与 SSE | 修改入口或外部契约时 |
| [04-domain-layer.md](04-domain-layer.md) | 聚合、值对象、领域服务、业务状态与事件 | 修改领域模型和业务规则时 |
| [05-infrastructure-layer.md](05-infrastructure-layer.md) | 数据库、模型、工具、检索、缓存、恢复、审计与观测 | 修改外部依赖、技术适配或运行机制时 |
| [06-daily-work.md](06-daily-work.md) | 需求、设计、变更、Review、验证、评测、发布与维护 | 开始任务、提交、评审及交付时 |

应用层职责集中在架构规范中；接口、领域和基础设施规则引用这条边界，不额外建立第七份重复文件。

## 哪些内容放 Rules

| 内容 | 放置位置 |
| --- | --- |
| 长期约束：依赖方向、编码约定、授权、事务、错误和验证要求 | 本目录 Rules |
| 具体接口字段、业务状态机、工具 Schema、表设计、预算阈值及评测政策 | 项目 specs/ 或实际采用的权威契约位置 |
| 新增工具、排查故障、执行迁移、发布等详细任务步骤 | 按需采用 Skill 或运行手册 |
| 系统当前模块、数据流、部署及信任边界 | ARCHITECTURE.md |
| 为何选用某数据库、端口位置及例外取舍 | ADR 或项目决策记录 |

规则负责要求“定义哪些契约、遵守什么边界”，不复制契约内容。不要把长篇背景、历史问题清单、完整评测数据、未经验证的 POM 或示例代码注入每轮上下文。

## 级别、冲突和验证

- **必须／禁止**：适用范围内的硬约束；修改时需要对应测试、工具检查或评审证据。
- **推荐／优先**：默认选择；已有项目约定或明确需求不同，可记录理由后取舍。
- 先遵守当前任务的明确要求和适用的项目约定；发现与本目录有实质冲突时明确指出影响，记录决定，不自行扩大权限或静默取消安全控制。
- 每个采用项目指定规则维护者。例外记录影响、补偿措施、批准人及失效条件；工具配置和规则文档同步维护。
- 文本规则不能自动阻止越权、数据丢失或依赖越界；需要在服务端授权、测试、数据库约束和 CI 中落实。没有实际验证，不能声称门禁已生效。

## 如何放到项目中

将整个 rules/ 目录复制到目标仓库。根据所用编码工具配置实际读取方式；普通 Markdown 文件夹本身不保证自动加载。

如果项目使用 AGENTS.md，可以将下面的指引合并到现有根文件中，保留原有项目要求。以下内容只是接入示例，本规则包不会修改当前聊天或目标机器的全局设置。

```markdown
## 项目工程规则

开始开发、重构或评审时，先阅读：
- rules/01-architecture.md
- rules/02-coding-style.md
- rules/06-daily-work.md

根据修改范围补读：
- 接口／消息入口及契约：rules/03-interface-layer.md
- 业务模型、不变量及状态迁移：rules/04-domain-layer.md
- 数据访问、模型、工具、消息和运行恢复：rules/05-infrastructure-layer.md

同时阅读被修改模块的现有实现及相关 Spec。
只执行仓库实际提供的构建、检查和测试命令；不虚报结果。
```

## 接入时确认

- [ ] 仓库明确 Java、Spring Boot、Spring AI（如使用）、数据库及构建工具的实际版本。
- [ ] 包结构与本规则描述的职责对应；已有架构通过映射适配，不为包名批量搬迁代码。
- [ ] README 或现有项目文档给出真实的快速验证和完整验证入口。
- [ ] formatter、静态检查、测试及 CI 的实际配置与规则一致。
- [ ] 业务契约、风险策略、预算及评测阈值有明确来源，不引用未配置的占位值。
- [ ] 规则读取方式已在所用工具中核验；不把“存在目录”当成“已经自动生效”。

本目录是整理后的规则文件，不包含业务脚手架、测试实现或 CI 配置。

## 配套方案流程

完整工程包还提供以下按需资产：

- `skills/task-to-design/SKILL.md`：需求分级、WBS、技术方案和边界验证流程。
- `skills/task-to-design/assets/tech-design-template.md`：Skill 自带的模板；Skill 文件夹可单独分发。
- `docs/templates/tech-design-template.md`：可直接放进目标仓库的十二项技术方案模板。

这些路径以完整工程包根目录为基准；仅下载 Rules 包时不包含配套资产。完整流程按需读取，不注入每轮 Rules。项目模板与 Skill 资产在本次打包时保持一致；项目后续定制以其仓库模板为准。
