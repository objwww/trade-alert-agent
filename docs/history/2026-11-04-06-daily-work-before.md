# 日常要求规范

适用：需求澄清、开发、评审、验证、发布及维护。根据变更风险执行，不要求所有小改走同样重的流程。

## 开始任务与设计

- **DAILY-01｜必须**：确认目标、验收条件及影响范围，阅读现有实现、调用方、相关 Rules 和 Spec；先利用仓库已有信息，只有必要信息缺失时再澄清。
- **DAILY-02｜必须**：影响授权、外部副作用、公开契约、数据兼容、恢复和成本上限的变更先明确设计；小而确定的变更可在同一 PR 更新契约，跨团队或方向不明的变化先评审设计。
- **DAILY-03｜必须**：具体契约、业务状态、阈值和字段放 Spec／Schema；任务步骤放运行手册或 Skill；系统现状放 ARCHITECTURE.md，重要取舍放 ADR，避免在 Rules 复制全部内容。
- **DAILY-04｜优先**：以小变更解决当前问题，复用已有技术；不顺手重构无关模块，不预建将来可能使用的依赖与功能。

## 任务分级与方案证据

- **DAILY-22｜必须**：按实际行为和影响分级，不按文件后缀豁免；提高付款限额、修改权限、模型路由、重试、预算或隐私配置均需重新评估风险。T1 为低风险局部变更，T2 为重要行为变更，T3 为资金、合同、高敏数据、不可逆副作用或高风险授权变更；信息不足时标记待确认，不默认把所有任务定为 T2。
- **DAILY-23｜推荐**：按可独立验收与交付的结果拆任务，写明依赖、风险和验证方式；人日只用于估算，不为满足一天阈值拆散必须一起验证的一致性改动。
- **DAILY-24｜必须**：T1 可在 PR 中写简短设计；T2 使用适用的方案章节，T3 及跨团队破坏性变更在实施前取得有记录的设计评审。已有 Spec 或 ADR 足够时引用，避免每个子任务复制一份完整方案。独立方案可采用项目实际提供的十二项模板。
- **DAILY-25｜必须（边界分析）**：覆盖相关的输入、权限、依赖、状态、资源和终止条件；关键并发及崩溃窗口有明确结果语义。设计阶段列计划验证标识，实现后关联具体用例／检查和真实证据；计划用例名不是测试通过证明。不适用项说明原因，阻断项记录负责人和解法。
- **DAILY-26｜推荐**：优先读取现有实现与对应版本官方文档；存在重要架构选择时按需比较开源项目，记录来源、版本／commit、许可、借鉴与不采用的理由，不固定要求每项任务至少调研两个项目。本流程只借鉴架构与契约，不复制实现、Prompt、注释或测试。
- **DAILY-27｜必须**：方案状态、实现状态及验证状态分开记录；允许提前发起草稿 PR。未通过适用的评审、关键检查或发布门禁不得合并／发布；已经获得的有效授权无需重复申请，既有投入和时间压力不构成豁免。

## 实现、分支与提交

- **DAILY-05｜必须**：维护现有项目风格及公共契约；发现规范冲突或必须偏离时明确记录影响与决定，不静默改掉授权、校验或数据约束。
- **DAILY-06｜必须**：保护共享历史及他人修改，不随意重写共享分支；采用项目分支规则。短分支和功能开关按需使用，不强制每日 rebase 或固定三天合并。
- **DAILY-07｜必须**：提交和 PR 清楚说明问题、最终行为、影响面、相关契约、验证和风险；有行为变化时同步必要测试和文档，纯格式或文档改动不强制新增单测。
- **DAILY-08｜推荐**：项目依赖自动版本或变更日志时采用 Conventional Commits；否则使用清晰提交信息，不为格式本身建立额外审批。

## 验证与评测

- **DAILY-09｜必须**：执行仓库实际提供、与改动匹配的格式、构建、检查和测试命令；明确快速与完整验证范围。未运行、失败或环境受限如实报告，不把“应当通过”写成“已通过”。
- **DAILY-10｜必须**：测试验证业务结果、关键边界和安全约束；涉及授权、预算、重复执行、恢复、取消及外部副作用时覆盖对应失败与竞态路径。修复应有能够暴露原问题的有效验证。
- **DAILY-11｜必须**：架构和 CI 门禁确认扫描到目标模块，并验证合法样例能过、越界样例会失败；不能以文档存在证明门禁已生效。
- **DAILY-12｜必须（AI 行为变更）**：模型、Prompt、工具 Schema、策略或编排变化执行受影响评测和核心安全回归；重要发布或影响不明时执行完整发布评测。
- **DAILY-13｜必须（模型评测）**：控制流测试默认打桩，真实模型在受控流水线评估；记录数据、模型、执行配置及评判器版本，限制成本和期限，禁用真实生产写工具。供应商不可用报告验证未完成。
- **DAILY-14｜必须（质量门禁）**：按任务风险、样本及波动定义评测判定，区分百分点与相对变化；安全越权不能被平均分改善抵消。覆盖率、固定样本量及单次 2% 变化不作为无依据的统一真理。
- **DAILY-15｜必须**：CI 只检查格式，不自动 apply 修改源码后继续；避免无意义重复运行完整生命周期，不为追求数字编写无断言测试。

## Review、发布与运行

- **DAILY-16｜必须**：Review 检查职责、依赖、正确性、授权、事务、并发、兼容、取消／恢复和验证证据；格式交给工具，额外复杂度需要真实收益。
- **DAILY-17｜必须**：新增或升级依赖检查项目兼容、维护、许可证及安全影响；统一管理库与插件版本，不使用未经批准的动态版本或生产快照。
- **DAILY-18｜必须（发布）**：制品和执行配置可追溯到提交、依赖及评测结果；明确发布顺序、观察指标、停止条件及回滚／前向修复。不承诺不可逆数据变更可自动回滚。
- **DAILY-19｜必须（发布）**：适用的安全和关键正确性门禁失败时阻断；真实模型结果按项目发布政策决定，不将全部真实模型检查降为只观察。紧急例外遵循已有授权和补检制度，不自行扩大权限。
- **DAILY-20｜必须（运行）**：告警有责任人、处理入口和升级方式；重要故障记录影响、时间线、促成因素及有负责人的改进项。有效 badcase 脱敏复核后纳入回归。
- **DAILY-21｜必须**：规则、Spec、工具配置和实现保持一致；长期例外、版本升级及重要事故触发复查，过期规则及时删除。

## 交付说明

完成任务时说明：改了什么、行为为何变化、实际运行的验证与结果、尚未覆盖的限制及必要风险。引用真实文件和产物，不宣称未交付的模板、脚手架或配置已经存在。
