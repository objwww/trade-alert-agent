# 技术选型与取舍记录

日期：2026-11-02｜设计版本：0.1｜状态：待评审。下面的“采用”表示本次提出的设计决定，不表示依赖已安装或能力已实现。选型围绕目标一的场景与契约；运行实现按后续目标验证。

## 1 决策依据与比较方法

先满足既定 Java／Spring、DDD 四层、Docker／Compose／虚拟机、并发调查、证据可核验及测试留痕约束，再比较初期运维成本、契约稳定性、故障恢复复杂度和演进成本。不以框架流行程度或组件数量评分，不编造压测与质量提升百分比。

本轮可核实资料：已有 Rules、用户提供的 H05—H21 相关 PDF、谷粒商城固定提交的检查记录，以及下列公开来源。PDF 为背景设计，不是已实现证据。未取得业务运行环境、生产容量、身份提供方、真实业务基线；这些不会用虚构数值填补。

## 2 设计决策

| 决策 | 本次选择与原因 | 比较后首期不采用的方案及原因 | 代价与重新评估条件 |
| --- | --- | --- | --- |
| 应用组织 | RCA 采用模块化单体，内部 DDD 四层；API 与 Worker 是执行角色，可同应用部署 | 为 Planner／专家／Reviewer 各建微服务：当前没有独立扩缩容与团队所有权证据，会增加认证、状态与部署协作 | 单 Run 受 Owner 容量约束；出现经压测证明的独立扩缩容需求再拆 |
| 调查运行控制 | 薄 Harness 管理领域授权、预算、计划版本和提交，复用 Spring AI 的模型与工具协议 | 直接将 SDK 自动循环视为领域运行时：无法据此证明每轮授权、预算与提交满足本项目契约 | 我们承担状态机与恢复的实现成本；后续用可恢复性测试衡量 |
| 运行引擎候选 | 首期设计使用 PostgreSQL 持久状态＋受控调度，运行引擎留在应用端口之后 | Temporal：具备持久工作流能力，但会增加服务端及工作流发布运维；领域证据和权限仍需实现。不是认为它不支持动态 Agent | 若长任务、定时恢复、跨团队工作流成为主要维护成本，做等价故障矩阵 PoC 后再决定 |
| Agent 框架候选 | 先明确自己的 Task／Finding／Review 协议，再验证 Spring AI 基础执行能否覆盖 | Spring AI Alibaba Graph／Agent Framework 不整体接管第一版状态真源：其并行、持久化、上下文等能力可复用，但须证明与 Run Owner、Attempt、计划成员关系及原子提交契约兼容 | 不重复实现已有底层协议；目标八可将框架作为执行适配候选，兼容测试通过后调整 ADR |
| 调查存储 | RCA 控制面选 PostgreSQL；事务、唯一约束、条件更新管理权威状态 | 将谷粒商城 MySQL 业务库同时当调查库：会把实验业务与调查生命周期、权限和负载耦合。MySQL 自身也能支持多种领取机制，本选择不基于“它不能并发” | 多维护一套数据库；目标二锁定受支持版本，目标七验证领取、锁竞争、索引和恢复 |
| 工具数据 | Evidence 元数据及有界快照独立保存，较大内容通过存储端口扩展 | 原始日志全塞 Run JSON：放大状态读写；只存查询条件：源数据过期或延迟写入后难复核；首期强制对象存储集群：目前无容量证据 | 保存大小／保留策略需实测；超过数据库快照预算时引入对象存储，不改变证据引用协议 |
| 契约表达 | 人读 Spec＋JSON Schema Draft 2020-12；HTTP 在 OpenAPI 3.1.x 描述并引用同一结构 | 只用 Markdown：无法统一检查结构；只用 OpenAPI：无法覆盖领域跨字段不变量；Protobuf 优先：当前没有已确认的跨语言高吞吐二进制传输需求 | JSON Schema 不证明授权与因果；Java 语义校验不可省。OpenAPI 工具链小版本目标二核验，文档 3.1.1 仅作语义参考 |
| 内部主键／公开编号 | 内部 UUID v4；公开使用中文事件＋服务＋领域＋日期及原子序号；指纹另存 | 自建 Snowflake：额外机器号和时钟管理；只用 UUID 对外：不符合用户可读编号约定；Redis 独立发号：首期增加一致性与运维依赖 | UUID 随机索引与计数器热点需监测；序号按词典稳定代码分桶，允许空号，不承诺按提交完成时间严格排序 |
| 状态建模 | 生命周期、执行阶段、证据覆盖、结论及业务恢复分开 | 一个 SUCCESS 字段表示所有成功：会混淆任务执行、根因正确和故障恢复；直接沿用背景 PDF 中混合阶段枚举：与当前 DOMAIN-04 不一致 | 字段更多但语义可核验；状态迁移表与 Schema 同版本发布 |
| 计划与并发 | 每个 Run 一个有效 Owner，Run 内有界并行；同 Incident 可有多个独立 Run | 第一版把所有 Task 分发给不同 Worker：增加跨 Worker 合并和重规划协调；默认每个 Incident 只能一个 Run：阻碍独立复查与评测对比 | Run 预算及提交真源必须统一；以后 Task 分布式调度需独立设计 |
| 事件交付 | 本库状态＋必要 Outbox 同事务；调度通知可扫描重试 | 首期为所有状态变化增加 Kafka／RabbitMQ：引入双写与消费运维；只用内存事件：进程退出后可能丢失推进信号 | Outbox 清理和积压需监控。谷粒商城已有 RabbitMQ 是业务靶场组件，不等于 RCA 必须复用其内部队列 |
| 工具与协议扩展 | Gateway 统一治理；MCP 是可选外部适配；Skill 是经审核的调查方法 | 所有能力先做 MCP Server、每种工具包装独立 Agent、安装任意 Skill 脚本：未带来已证明的收益且扩大信任边界 | 工具／Skill 版本需固定，跨系统复用需求明确后再开启对应适配 |
| 观测与界面 | 沿用靶场现有兼容链路接入；前端沿用 Vue 方向和已有设计确认规则 | 为统一图上的品牌立即将 Zipkin 迁移 Tempo、重写商城前端、引入 Kubernetes：不属于目标一且增加靶场改动 | 数据源通过适配器保持业务语义一致；具体组件版本和基线在目标二／三验证 |

本表是针对当前目标的工程判断。没有对比压测，不声称所选方案在吞吐、成本或正确率上优于候选。

## 4 官方技术依据

- PostgreSQL 的 SKIP LOCKED 可以用于队列式消费者领取，但不能据此获得外部操作只执行一次保证。采用短事务领取，租约及 Epoch 另管执行资格。[PostgreSQL 17 SELECT](https://www.postgresql.org/docs/17/sql-select.html)
- Activity 的外部作用需要考虑幂等，重试与本地恢复不能替代下游业务保障。[Temporal Activity Definition](https://docs.temporal.io/activity-definition)
- Draft 2020-12 提供结构、引用与验证语义；format 的注解与断言是不同词汇表，实施时必须配置实际格式检查。[JSON Schema Draft 2020-12](https://json-schema.org/draft/2020-12)
- OpenAPI 3.1 的 Schema 与 JSON Schema 2020-12 对齐，但不能替代资源授权及业务状态校验。[OpenAPI 3.1.1](https://spec.openapis.org/oas/v3.1.1.html)

这里引用 PostgreSQL 17 和 OpenAPI 3.1.1 是固定语义依据，不声称它们是当前最新版，也不据此锁定生产补丁版本。
