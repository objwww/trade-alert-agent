# Task to Design 流程验证记录

日期：2026-11-01。对象：本包 task-to-design Skill、技术方案模板及日常 Rules 的增补。

## 验证方式

先以原工作流摘录执行 5 个独立上下文基线，再提供修订 Skill 执行 5 个独立上下文样本。共同业务场景为：Java 21／Boot 3／MySQL 8 多实例项目；无幂等接口的付款工具可以按业务单号查询；同时处理文档错字、提高付款限额、付款成功但本地未提交即崩溃三个任务。施加发布时间、评审缺席和已实现一半三类压力。

测试代理只给流程决定，不访问生产、不改业务文件、不调用真实工具或模型业务接口。结果用于验证规则如何影响决策，不代表完成了 Java、数据库、资金或生产系统测试。

| 样本 | 风险与流程观察 | 未知付款处理 |
| --- | --- | --- |
| 原稿1 | 保留配置豁免，恢复按默认T2；全部验证后发PR | 主动要求查询／对账，不盲重付 |
| 原稿2 | 保留配置豁免，恢复按默认T2；全部验证后发PR | 主动要求查询／对账，不盲重付 |

| 原稿4 | 识别豁免冲突并按T3；仍保留统一调研和方案负担 | 主动要求查询／对账，不盲重付 |

基线1／2的提示词没有独立强调“资金T3”，其余样本强调了该条。这些结果只用于定性发现原流程歧义，不作为严格对照或统计显著性的证据。全部基线已经主动阻止盲目重付，不能将这项能力归因于新 Skill。

## 修订稿观察

| 样本 | 风险、设计与 PR 决策 | 恢复与证据 |
| --- | --- | --- |
| 修订1 | 文档T1，两项资金T3；允许共享方案和提前草稿PR | 分析五窗口；明确无仓库、未验证；未知结果查询核对 |

| 修订3 | 按实际行为分级；T3设计先行，可先发草稿 | 明确五窗口、全局配额及查询延迟；不虚报通过 |

| 修订5 | 给出WBS；两项资金T3；草稿、合并、发布分别判断 | 核对外部结果及金额，未证明旧请求失效前不重付；不虚报文件和证据 |

五个修订样本均识别配置改变资金风险，允许提前草稿 PR，不因倒计时或已投入工作而跳过高风险门禁。样本4额外使用“三次未明转人工”的数字；该次数不是本 Skill 确立的通用政策，实际实施仍须按任务风险确定。此结果说明仍需审阅具体产出，不把小规模场景检查称为对所有任务的保证。

## 静态与文件检查

- 官方 skill-creator 的 quick_validate.py 已执行，返回 `Skill is valid!`，仅证明其静态检查项通过。
- 项目模板和 Skill 随附模板已核验内容相同；检查了十二项结构、七列矩阵、十个边界示例、规则编号及本地引用。
- 验证脚本同时核对压缩包文件清单及解压内容是否与交付文件逐字节一致；最终交付前重新执行。
- 文件包不安装全局 Skill，不更改工具设置，也不提供可被误认为已实现的 POM／ArchUnit 或业务代码。

## 验证边界

基线和修订样本均为少量文本场景，不能证明所有任务均能正确处理。原文未提供完整 v1.0／v3.0、真实业务仓库或团队审批制度；接入后仍需验证真实授权、SDK 默认行为、数据库竞争及故障恢复，并使用项目实际命令完成门禁。
