## Codex 裁决与一致性边界

1. DOMAIN-11 原文允许外部领域契约 I/O 的例外不采纳：与 ARCH-04 的 domain 不执行 I/O 直接冲突。保留抽象声明，外部调用经 engine 编排。此为显式收紧，非仅替换语言名。
2. DOMAIN-07 不强制所有对象可哈希；冻结写法引用 CODE-12，原 record/equals/hashCode 迁移为 dataclass/值比较/按需哈希。
3. DOMAIN-08/09/14/15、INFRA-04～21 按场景显式条件化。告警通知所需恢复/可靠交付并未成为可跳过事项；条件在本项目已触发的仍须实现。
4. INFRA-10 当前单实例防双开；多实例原子领取与 fencing 只有经架构变更批准才适用，不提前建分布式机制。
5. INFRA-03 确认无副作用的失败可按契约重试；unknown 遵循 ARCH-17/36/42，不把“超时”推断成确定失败。
6. INFRA-13 保留状态/事件原子提交与先持久化后入队；不强制 Outbox 命名或消息中间件。外部通知不纳入本地事务，不承诺通道全局恰好一次。
7. INFRA-15～21 只作未来能力启用条件，不扩大当前模型、工具、RAG、MCP、沙箱需求；Spring Advisor 不照搬为 Python 依赖。
8. Pydantic 边界沿用 ARCH-33/API-03；不进入 domain，也不推导每个适配器都必须使用。金额舍入、商城采集、数据库与驱动均待实际核验，不预设。
9. 六目录及源码方向仅由01维护；04管领域不变量、05管适配和持久化落地、02管语言、03管协议。共同规范只引用。
10. 迁移顺序：01 → 02/03 → 04/05（本次首版）→ 06（日常与验收，待迁移）→ 全套一致性复核 → MVP-01方案与自检 → 规范及方案确认后派发。无论文字落稿或静态检查成功，均不等于独立验收或获准开发。
