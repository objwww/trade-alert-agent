# Task to Design

## S — Scope

将需求整理为可验收任务和与风险匹配的方案。沿用仓库已锁定的 Java、Boot、Spring AI 和数据库，不假设跨版本 API 兼容。

修改前读取实际存在的 AGENTS.md、相关 Rules、ARCHITECTURE.md、Spec 及实现；缺失时明确缺口。未经提供的“v3.0 第10章”不是可引用证据。

## Default Assumptions

| 风险 | 可观察条件 | 设计深度 |
| --- | --- | --- |
| T1 | 局部、低风险、可逆，未改变公开契约或安全边界 | PR 简短说明和相关验证 |
| T2 | 重要行为、模型／Prompt／工具契约、DDL 或并发策略变化 | 独立方案或引用已有设计，填适用章节 |
| T3 | 资金、合同、高敏数据、不可逆副作用或高风险授权变化 | 实施前满足项目设计评审，明确核对与恢复 |

按行为分级；配置、测试或文档改动若改变生产授权、限额、数据政策等，同样评估。信息不足写“待确认及其阻断项”，先推进独立分析。

按可独立验收结果拆分，估算不作为一天硬上限。现有设计足够时引用；不强制每子任务单独方案，不固定两个开源项目名额。

## Mandatory Rules

1. 关键边界记录检测、状态语义、处置、恢复和验证；设计阶段列计划标识，实现后附真实用例及结果，不能用用例名证明已测试。
2. 写调用结果未知时，按稳定业务标识查询／对账；不能盲目重试、跳过必需动作或仅重放最后成功 Step。查无记录可能只是延迟，重发须证明先前请求不会再生效。
3. 并发和恢复按实际数据库及部署验证：进程内 Semaphore 不等于全局配额，MySQL 不照搬 PostgreSQL 部分索引。
4. 只借鉴架构与契约；不复制外部实现、Prompt、注释和测试；不编造版本、commit、许可证或文档。
5. 草稿 PR 可提前创建；评审、实现、验证和发布状态分开。适用评审未完成或关键验证失败不默认合并／发布。已有有效评审和授权直接引用，不重复申请；时间压力和已投入工作不构成豁免。

## P — Process

### Step 1 风险与 WBS

确认目标、验收及影响；输出“任务ID｜可交付结果｜依赖｜风险及理由｜验证｜估算”。按真实资金／权限影响分级，识别可独立推进部分。

### Step 2 依据与借鉴

先看现有实现与对应版本官方文档；重要选择按需比较开源，记录链接、版本／commit、许可核验、借鉴点、不采用理由及验证方式。已有证据可复用；不存在的材料标为未取得。

### Step 3 方案

优先用项目的 docs/templates/tech-design-template.md；无模板时将随附 [方案模板](assets/tech-design-template.md) 复制到该位置。T2/T3 方案通常保存 docs/design/{编号}-{名称}.md。十二项按适用程度填写或引用，不适用写理由；未决项写负责人、解法和阻断性，不用空话掩盖风险。

### Step 4 边界、恢复与证据

按模板填写七列矩阵；检查输入／权限、依赖、状态／并发、资源和终止。展开 F1—F5，尤其核验意图前、调用前、结果未知、成功未提交、提交未通知五个窗口。为每个关键场景安排可执行验证。

### Step 5 评审与回归

按风险及现有授权记录决定可实施范围；需要审批的高风险工作保持待评审，其他工作继续。实现后更新 Spec，执行真实项目命令及必要模型评测；失败、未运行和环境阻塞如实记录，按项目门禁决定合并／发布。

## O — Output

按顺序交付：风险及依据 → WBS → 方案文件或已有设计链接 → 边界验证映射 → 评审／实现／验证状态及剩余阻断项。

示例：提高自动付款限额属于资金风险，即使只改配置也按 T3；先完成设计和权限评估，可发草稿 PR，未获适用评审及验证不得上线。付款恢复先核对外部业务单号，未知结果暂停重付。

## Regression Checklist

- 风险是否按行为而非文件类型判断？设计深度是否适当？
- 关键权限、参数、并发和副作用窗口是否明确？
- 计划验证是否已区分真实执行证据？没有编造命令通过或审批？
- AI 行为变化是否有对应评测；模型不可用是否标为未完成验证？
- 灰度和恢复是否说明在途任务、数据及外部副作用？
- 交付是否仍有阻断项；草稿 PR、合并和发布是否分别判断？
